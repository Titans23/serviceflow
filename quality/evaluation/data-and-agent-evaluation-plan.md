# ServiceFlow 商品、知识与 Agent 评测方案

2026-11-27 · 工程设计。下文的样本配额、发布门槛和排期均为建议值。已有实测单列在第一节。

建议先验证两个客服任务。顾客问某款手机的无线充电需要什么配件时，客服应给出适用型号和条件。顾客取消已付款订单、确认响应丢失时，仍应能查到结果，退款只生效一次。前者需要可追溯的商品和手册，后者需要可复现的订单初态及独立的退款记录。把这两条链跑通后，再把中文测试会话扩到万级。

## 3. 商品和手册怎么取得、入库和更新

| 内容 | 首选渠道和无供应商时的起步方式 | 落库与事实边界 |
| --- | --- | --- |
| 商品主数据 | 有合作商家时取 PIM/ERP 导出的 CSV、JSON 或约定 feed，取得 SKU、品牌料号、地区、变体和可用的 GTIN。个人项目可从现有目录开始，按 Open Icecat 账号可用品牌逐个核对型号、语言、使用与再分发范围。缺失 GTIN 留空。 | 商家 SKU 作目录键，有 GTIN 时作交叉核对。品牌、型号、地区、容量一起判定变体。保留原值、单位、标准化值和来源。通过已有管理 API 写 MySQL 的 `product`。[导入器](../../scripts/evaluation/import_retail.py) |
| 店铺价格、可售状态、订单 | 报价由商家提供，记录币种、含税口径和生效时间。个人项目可自定店铺测试报价、两名合成顾客和订单，标为合成，只在评测实例使用。 | 未核报价保持 `listPrice=null`，演示用 `OFF_SALE` 仅代表该店设置。订单、付款、库存情形与品牌规格分开。实际退款金额从原订单读取。[事实来源 ADR](../../docs/adr/0002-facts-rag-separation.md) |
| 使用、兼容与保修手册 | 优先由品牌或经销商提供允许索引的对应地区 PDF、HTML 或 Markdown，以及版本和适用型号。华为官网可作具体规格和服务入口的核对线索，其条款限制自动采集和商业使用。无批量授权时，先采用项目自有的取消、退款、人工接手手册。如需可分发的长文档对照，可选 Raspberry Pi 官方文档仓中的硬件章节，按文档的 CC BY-SA 4.0 标明作者、版本、修改和许可，单独打包。 | 厂商保修和店铺售后各有发布主体。整本资料分别记录内部索引、提交外部模型、公开分发三项使用范围。范围未明的资料先留链接和待核状态。[华为规格示例](https://consumer.huawei.com/cn/phones/pura80-pro/specs/) · [华为使用条款](https://consumer.huawei.com/cn/legal/terms-of-use/) · [Raspberry Pi 文档许可](https://github.com/raspberrypi/documentation) |

**交付单位是一份可追溯的数据包。** 沿用 `catalog.json`、`manifest.json` 和 `knowledge/`。在清单补充每项事实或章节的来源定位（页码、标题、表格行与脚注）、型号/SKU、地区、语言、版本、生效期、核验人、使用范围、内容哈希。操作手册保留前置条件、步骤、例外和单位。扫描件经 OCR 后人工抽核参数、表格和否定词。可用 LLM 提取字段草稿，要求每个值给出原文位置，缺失填空。两地规格冲突时保留两个出处并按地区复核。同型号不同容量共享源章节 ID。

入库顺序为“检查授权和格式 → 规范化并去重 → SKU 更新到 MySQL → 管理 API 上传文档 → Outbox/RabbitMQ 投递 → 消费者解析、分块和嵌入 → 写入 Milvus → 核对 MySQL 中的活动版本和实际命中分块”。记录“来源章节 → 文档版本 → 实际 chunk ID”映射及嵌入模型、向量维数、分块和中文分词配置。选一款相似型号作反例，再测一次资料更新，验证新条件可检索、旧版本退出当前回答、入库失败时旧版仍可用。冻结回归集固定历史快照，日常资料随商家变更生成新包。[知识版本实现](../../docs/wiki/knowledge.md)

现有导入器整包提交，商品服务每批最多 500 条。首批可复用现有上限。扩到数千 SKU 时按批记录回执，逐个核对版本与哈希后续传。当前包校验限定四个厂商域名且要求每个 SKU 有文档。新来源和自有手册应通过有来源类型、使用范围与明确域名的新包版本接入。对缺手册商品登记 `catalog_only` 并安排资料不足测试。现有 v2 校验继续覆盖历史包。[商品服务](../../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/ProductServiceImpl.java) · [现有包校验](../../scripts/evaluation/eval_v2.py)

首轮优先补手机、耳机的设置、兼容、保修与店铺售后。建议首个扩充里程碑为**累计 30 款型号、80–120 个 SKU、至少 20 份独立手册或政策**，至少纳入两对可验证的新旧版本。相似型号可以考验商品识别，但商品一旦选定，检索候选就按商品和活动版本过滤。要测检索难度，还要在同款商品下放入容易混淆的有线/无线、随附/选购、设置/故障排查章节。分别报型号、独立资料与章节数、有手册 SKU 占比，以及每题过滤后的候选章节数。[业务检索链路](../../docs/wiki/rag.md)

## 4. 从 200 个候选会话扩到 10,000 个

**一份测试样本是一项有目标的客服任务。** 由程序生成合法初态和故障条件，由人依据政策或产品资料定义可接受结果。LLM 的产物是顾客的自然表达和追问。参考答案中的金额、订单归属、授权条件、章节证据和最终状态均可从独立来源复算。

| 首轮任务 | 蓝图数 | 必含差异 |
| --- | ---: | --- |
| 申请取消、确认与退款恢复 | 20 | 仅询问、明确确认、拒绝、过期、切换订单、其他顾客的订单、响应丢失、重复通知 |
| 商品识别与比较 | 10 | 错别字、简称、普通版/Pro、容量、配件、缺报价、候选要澄清 |
| 手册、政策与不足 | 10 | 单段、多段、相邻干扰段、部分可答、无答案、旧版本、跨地区 |
| 订单、物流、退货与工单 | 6 | 未付款、已发货、查询进度、人工接手、同一工单后续沟通 |
| 跨轮切换与纠正意图 | 4 | 查完 A 改问 B、否认取消、打断后继续、缺少上下文 |

1. **先冻结蓝图和事实。** 每份保存 `family_id / split / source_version / fixture_seed / actor / user_goal / allowed_actions / required_facts / forbidden_facts / milestones / expected_final_state / fault`。金额从夹具推导，目标状态由人工审定的业务状态转移表给出，知识要求由源章节给出。状态表独立于被测服务实现。旧执行器的 `chat/confirm/http` 步骤可复用。现有 v2 只接受项目编写来源和两种 split。新版本需要显式支持 `llm_synthetic`、裁判验证集和渠道观察，并记录样本与父蓝图的关系。[执行器](../../scripts/evaluation/eval_v2.py) · [合成订单夹具](../../scripts/evaluation/prepare_v2_fixtures.py)
2. **离线批量写用户话术。** 给生成器的输入只有顾客可知的商品、目标、已知信息和语气。提示词示例为“你是刚付完款的顾客。先问能否取消，只有客服解释后才决定。写四种中文开场，包含简称、口语或省略。仅返回用户发言、风格和仍需澄清的信息”。保存模型版本、提示词哈希、采样参数、父蓝图和生成批次。独立程序用结构化约束核对金额、型号、否定和本人/代办意图。语义筛查标记歧义，人工抽审决定采用或改标。
3. **多轮保留两种执行方式。** 固定脚本便于在两个版本上回放相同意图。交互测试则用有限状态的模拟顾客，依据真实客服上一轮选择补充型号、拒绝、确认或请求人工。顾客模型只看会话、私有目标和允许透露的事实。执行器持有测试身份，仅在脚本允许且收到对应确认卡时模拟点击。设最大轮数和停止条件，保留目标未完成、模拟顾客违规和超时三种结果。
4. **按族隔离后再扩写。** 先分配开发、裁判验证、封存端到端测试，建议按独立任务族约 70% / 15% / 15%。同一蓝图的改写、同一手册派生版和近重复归到同组。新来源盲测再整体留出厂商或来源族。共享的店铺规则明确标为已知规则。封存题、答案与提示示例、训练集逐项查重，公开仓仅登记盲集版本与哈希。已调过的华为题和 Apple/Samsung 首轮结果保留作已见回归。
5. **按质量扩容。** 试点 50 份蓝图 × 4 种表达 = 200 个候选。通过后扩到 1,000 个不同任务蓝图 × 最多 10 种表达 = 最多 10,000 个候选会话。用规范化哈希、中文字串重合度和语义相似度筛查近重复。“能取消吗”和“帮我取消”应成对保留，因为操作权限不同。试点每族至少人工抽一条，身份、金额和确认语义变化全部复核。作为首轮扩容条件，可定为跨集同族泄漏 0、金标引用有效率 100%、分层抽检的意图保持率至少 90%。未达标的类别先修种子或提示词。

万级生产按批写入逐行 JSON。每项以蓝图、变体序号和生成配置确定唯一键，记录候选、拒收理由、复核状态与输入输出哈希。中断后从缺失项续作，保留首轮结果。每批公布生成数、格式合法数、去重后数、抽审接纳数、最终可执行会话数、独立任务族数。固定脚本可全量回归，昂贵的交互试验从各业务和风险层预先抽组。

目前没有 ServiceFlow 真实流量分布。上表是覆盖配额。以后取得使用许可时，可在本地用脱敏汇总的意图占比、轮数、输入长度、澄清率、否定与改口率校正采样，再抽样盲评语言自然度与业务可行性。保留一套按业务分布加权的成绩，另报高风险压力集，两者各自保留分母。

## 5. LLM-as-Judge 怎样评分

每次评测保存三份结果。**程序断言**读授权、工具参数、数据库和渠道。**独立模型裁判**评用户看到的答复。**人工证据裁决**处理抽检、分歧和重大问题。线上 RAG Grader 的职责是筛选候选证据，现有 `semantic_review.py` 提供可复用的证据组装、来源 ID 校验、错误记录和按场景数限制调用的入口。独立裁判尽量与生成器、被测客服采用不同模型系列，冻结模型标识、提示词和评分版本。[现有语义筛查](../../scripts/evaluation/semantic_review.py)

裁判输入包括逐轮会话、实际回答、顾客已透露的目标、当时可见的证据、独立标注的必要/可选/禁止事实、适用版本及该轮业务状态快照。隐藏被测版本名、生成器、规则分数和其他裁判意见。候选回答与证据均作只读材料。裁判逐项返回 `dimension / score / claim / evidence_ids / reason / severity`。分数为 0、1、2，任务预先定义不适用维度。客服虚构来源按事实错误扣分。裁判引用不存在的 ID、评分不合约或运行轨迹缺失时，记录评分错误或待复核。有完整记录且确实检索不到资料时，仍可正常评“是否恰当说明不足”。

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 事实与依据 | 每个实质断言由当前商品、活动文档或当轮业务快照支持 | 核心事实正确，个别次要表述的依据不清 | 编出参数、价格、政策或到账，串型号、订单或地区 |
| 完整性与回答范围 | 覆盖必要事实和关键限定，补充内容切题 | 缺次要条件或混入无关段落 | 漏掉关键条件、漏答核心目标或给出相反结论 |
| 状态与不确定性 | 分清待确认、处理中、成功、未知。歧义时澄清，部分可答时分别说明 | 判断方向正确，边界表述含混 | 把待确认说成已执行，把处理中说成已到账，或无证据给出确定承诺 |
| 对用户的帮助 | 回答简明，需行动时给出可执行的下一步 | 用户仍能继续，指引略含糊 | 答非所问，或指引用户做无效、错误的操作 |

**建议通过规则。** 适用的前三维各为 2，帮助维适用时至少 1。四维均适用时，最低通过分为 7/8。发生未授权写入、错单错款或重复生效，整例直接失败，各维分数保留供诊断。当订单已取消、退款仍在处理中时，“已取消，退款处理中，可到订单详情查看”符合快照。“钱已到账”在事实和状态维均为 0。

**校准与误差。** 两名熟悉业务的人独立盲标，分歧回到指定页段或数据库快照，由第三人或共同复核定案。建议扩容阶段用 100 条开发答案改评分细则，冻结裁判后用不同任务族的另 100 条验证。验证集至少有 60 个独立严重错答，另含正确、部分正确和正确拒答。可从系统真实运行中取答复，也可人工植入“已到账”“错订单”等错误。两种来源分别统计，保留全部人工标签和分歧理由。

公布人工之间、裁判对人工的逐维一致率、加权 Cohen’s κ 和通过/失败混淆矩阵。漏放率分母是人工认定的严重错答数，误拒率分母是人工认定的合格回答数。建议裁判验收时 100 条都有可核评分，各适用核心维 κ ≥ 0.70，全部严重错答零漏放（至少 60 条），合格回答误拒率 ≤ 10%。0/60 的单侧 95% 精确上界约为 4.9%，解释限于独立抽样假设下的该类挑战题。缺少人工校准或未达门槛时，报告模型筛查结果及待裁决数。版本对比交换 A/B 顺序并允许平局，两次结论冲突进入复核。正式批次复核全部重大分歧并随机抽查 10% 的模型通过项。

## 6. 用什么指标验收整套系统

| 指标 | 定义和分母 | 用途或初始验收建议 |
| --- | --- | --- |
| 端到端任务成功率 | 同时满足必要中间约束、目标终态和适用语义要求的场景数 / 计划场景数。报告计划、完成、错误、待裁决、未执行数。 | 按商品、RAG、取消、恢复等任务族以及风险分层。先取得基线，再预注册版本比较目标。 |
| 工具与参数正确率 | 必需调用发生且关键参数匹配的次数 / 预期必需调用次数。另记多余调用与禁止的写调用。核对主体、目标订单、动作编号、金额和批次，由可信运行时绑定的字段单独标记。 | 调用的允许顺序按业务里程碑约束。等价只读查询路径可通过。 |
| 未授权副作用率 | 观察到订单、支付、退款或工单禁止变更的场景 / 有完整观察的应拒绝或应澄清场景。另报确认前写入、跨主体读泄露、错单写入。 | 严重事件 0，且计划的高风险场景观察覆盖 100%。待确认卡、审计记录等允许写入按动作白名单处理。 |
| 重复退款与恢复 | 新增重复有效退款的业务单数 / 完整观察的可重放业务单数。故障后在时限内达到指定状态且无多余副作用的场景 / 计划故障场景。另报错误终态、人工接手和恢复时长 P95。 | 重复生效和错额均为 0。正常完成、仍待核验、正确转人工分别计。每题预定终态和等待时限。 |
| 检索与回答 | 在可回答题上宏平均必要章节 Recall@5、首个相关章节 MRR@5。另报必要事实覆盖、有效引用支持的断言 / 可核断言、无答案题正确拒答、可回答题误拒、部分可答题完整率。 | 分商品/版本过滤前后、检索前五与 Grader 后证据分别归因，源章节跨 SKU 副本去重。 |
| 多次可靠性 | 预先选定任务，每题用等价新夹具独立跑 3 次。三次全部成功的任务数 / 计划重复的任务数即本批 pass^3，另列首跑与逐次结果。 | 同一试验内的幂等重放用原 ID，跨试验用新订单和会话。改写数、轮数、重复次数分别计数。 |
| 效率与成本 | 同并发报告首个正文时间、整轮与整任务 P50/P95、错误率、每成功任务花费。后者分子含失败尝试。分列入库、生成、被测系统、裁判的调用和费用。 | 区分预热与正式运行，注明服务端或客户端计时起止。缺 token 或账单时标未知并保留实测请求量。 |

每个比例给出分子、分母和区间。独立场景成功率用 Wilson 区间，零事件可给单侧精确上界。多种话术或多次采样按任务族聚类做 bootstrap。版本比较固定数据、夹具、故障、模型配置和并发，用相同任务族做配对。高风险题出现严重错误即阻断，缺关键观察记为结果不完整。主要业务失败、裁判错误、基础设施失败分别记账。

## 7. 隔离评测环境和一次完整验收

| 层次 | 运行入口和真实组件 | 交付证据 |
| --- | --- | --- |
| 离线数据与合约，每次 PR | Python 校验来源、哈希、分组、断言、标签和可执行性。新增生成器和裁判解析器可用固定输出做合约回归。 | 包清单、重复与泄漏检查、用例数及各类分母。[离线校验](../../scripts/evaluation/eval_v2.py) |
| 业务集成，每次 PR 或夜间 | 用独立 Compose、合成身份和订单运行 Spring 服务、MySQL、Redis、RabbitMQ。退款故障用持久化本地渠道、两个消费者和真实浏览器链路。Demo 模型用于确定性业务验收。 | 确认前后快照、渠道受理与生效记录、断线恢复后的 UI、事件与工单。[业务环境](../../deploy/evaluation-compose.yml) · [退款环境](../../deploy/refund-verification-compose.yml) · [运行手册](../../docs/guides/evaluation-and-refund.md) |
| 模型端到端，限额批次 | 在独立的现有 Cloud Compose 中组合真实聊天模型、Milvus、Embedding、Reranker、后台退款和本地模拟渠道。从顾客聊天 API 或浏览器进入，经过路由、会话、检索、确认、执行和回读。另用固定商品 RAG 入口定位检索差异。 | 同一会话关联 SSE、工具参数、引用的实际分块、动作、数据库和渠道。另报仅测 RAG 的结果。[整链环境](../../deploy/evaluation-cloud-compose.yml) · [RAG 诊断环境](../../deploy/evaluation-rag-v2.yml) |

现有退款演练可在仓库根目录用下列入口复现。最后一步会创建合成订单并重启专用验证容器，详细前置条件和浏览器接续步骤见[隔离环境运行手册](../../docs/guides/evaluation-and-refund.md)。

```powershell
python -B scripts/evaluation/eval_v2.py validate --suite quality/evaluation/datasets/refund-sandbox-v1.json
docker compose -p serviceflow-refund-verification -f deploy/refund-verification-compose.yml config --quiet
docker compose -p serviceflow-refund-verification -f deploy/refund-verification-compose.yml up -d --build --wait --wait-timeout 300
python -B scripts/evaluation/refund_delivery.py --allow-isolated-faults
```

新增整链批次应固定代码、镜像、语料、裁判和随机种子，核对隔离实例与预算，导入资料并验证活动版本，每次试验新建双用户及订单夹具。从 `POST /api/chat/sessions/{sessionId}/messages/stream` 或浏览器发起会话。测试程序独立控制故障注入和只读观察，按同一业务标识关联数据库与渠道，达到目标或场景超时时封存证据。并行试验使用独立订单、会话及渠道观察范围。现有夹具固定 99 元、取首个商品。测试多金额或指定 SKU 时，先让夹具按目标生成订单行，再验订单行、订单总额与退款一致。

**一笔确认响应丢失的订单如何验收。** 合成顾客 A 刚在同一会话查过一笔 `PROCESSING/PAID`、99.00 元的订单。顾客 B 另有一笔。这条任务预先约定最终应当退款成功。

| 时点 | 顾客或环境做什么 | 观察器必须看到什么 |
| --- | --- | --- |
| 提出请求 | A 在聊天中说“刚查的那单，帮我取消吧” | SSE 发出绑定 A、会话和该订单的 `action_required`。允许持久化 PENDING 动作。订单仍可取消，取消账本与退款请求增量为 0，渠道增量为 0。 |
| 用户决定 | A 明确点击确认。测试端在服务端提交后丢弃确认响应 | 动作为 CONFIRMED，目标订单 CANCELLED，一条取消账本和一条金额 99.00 的退款请求。B 的订单快照相同。 |
| 恢复与对账 | 顾客端用原动作读 `GET /api/chat/actions/{actionId}/result`，按本人订单查退款。另一个故障用例独立注入重复通知 | 客户端只读核验。最终退款 SUCCEEDED、付款退款状态 REFUNDED，渠道凭同一退款标识和金额生效一次。途中回答与当时状态一致，到约定时限仍未成功则本例失败。另设持续未知用例验收待核验或转人工。 |

另设镜像任务让 A 只询问或显式放弃，以及用 B 自己的测试会话核对权限。每个镜像任务使用独立夹具。对渠道端按试验前后新增的**全部**退款标识与数据库逐项对账，并记录 `accept_count`、批次和金额。现有模拟器的 `effective_refunds` 是单个退款标识上的 0/1 状态。一条记录无法发现另一个标识上的第二笔。如果要审计同一标识的每次资金模拟入账，下一步在模拟渠道增加只追加的生效流水，再按订单对次数和总金额。证据范围限于本地模拟渠道。[确认与只读恢复](../../docs/wiki/confirmation.md) · [渠道实现](../../apps/refund-channel/server.py)

整链盲测还应把两个入口串在一场会话里。顾客先问“这款手机的无线充电底座要另买吗”，再给出本人订单号，要求取消刚核对的那笔订单。第一段核查当前 SKU、活动章节以及配件的适用条件。第二段核查切换到正确订单、明确确认和渠道终态。一个场景编号能定位究竟是知识答错、上下文串单，还是退款恢复失败。

报告用 `run_id / case_id / trial_id` 关联数据及资料哈希、会话和动作的脱敏关联号、各阶段计时、程序断言、裁判版本与人工裁决。原始会话、模型出参、受限资料与运行凭据只在获准的隔离存储中使用。公共结果保留聚合、脱敏失败样例和复现所需的配置标识。

## 8. 首轮排期、费用与交付

| 建议阶段 | 工作量目标 | 进入下一阶段的条件 |
| --- | --- | --- |
| 第 1 周 | 复用已有 SKU，补两份可使用的手册、一个版本差异和一份自有售后流程。冻结 50 个任务蓝图及判断依据。 | 主数据可追溯、活动版本可回读、每个蓝图有独立可执行断言。 |
| 第 2 周 | 生成最多 200 个候选，完成按族抽检。先在免费业务环境跑取消、拒绝、错单防护、丢响应与重复通知。 | 两套账对齐。高风险场景证据齐全、严重事件为 0。保留首轮失败记录。 |
| 第 3 周起 | 新增独立任务族和来源，开展 100 + 100 条人工标注与裁判校准。先用小批真实模型在正常顾客入口跑通，再按验收结果扩到万级候选。 | 校准误差、数据接纳率、任务覆盖、成本与延迟均有实测。冻结首个独立端到端测试集再比较版本。 |

先算一次小批预算。例如每个蓝图一次生成四个候选，50 个蓝图需要 50 次生成。从中抽 40 个会话整段评分再需 40 次裁判。在这个固定脚本示例中外围调用共 90 次，另加被测服务实际的分类、检索模型、改写及其他调用。动态模拟顾客、复审和入库独立预算。各模型费用估算为 `输入 token × 输入单价 / 计价单位 + 输出 token × 输出单价 / 计价单位`，另计按请求收费的服务。用试点实测每个合格任务的成本再外推，区分报价估算和实付账单。启动付费批次前确认数据范围、供应商和费用上限，每次请求按最大输入输出预留预算，达到限额时保留部分报告。现有 Java 进程内限额需与生成器、模拟顾客及裁判的预算合并核算。[现有预算机制](../../deploy/evaluation-provider-budget.yml)

首轮交付是一份可重建的数据包、一份按族冻结的场景清单、一份经人工对照的中文评分细则，以及一份能从失败会话追到证据或退款记录的评测报告。本次仓库核查复验了商品主包、主集、退款专项、语义留出和 RAG v2 的离线数据合约，以及两套免费 Compose 配置。新增会话、人工标签、模型分数和线上能力数据仍待按上述批次取得。
