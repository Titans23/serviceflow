# ServiceFlow 最终版本交付报告

日期：2026-11-13。本文汇总第 1～4 批优化、P0 修复、P1 退货，以及本次完成的工单对话、知识恢复和 Agent 查询优化。这里的“最终版本”指当前商家客服业务范围的完整交付。

## 1. 这个产品现在给谁用，能办完什么事

ServiceFlow 面向有商品咨询与售后需求的顾客，以及处理售后问题的客服。顾客可以查商品、找到自己的订单、咨询物流与退款、确认取消、申请收货后退货，也可以把问题交给人工并持续追问。客服可以审核退货、确认实物收回、处理异常退款、回复工单和更新知识资料。

它的主要业务对象是已有订单。当前订单是合成数据，商品资料来自公开来源；项目没有购物车、真实交易下单或商家平台订单同步。退款由独立、持久化的本地渠道模拟服务执行，不转移真实资金。

| 用户遇到的情况 | 当前可以完成的操作 | 最终结果在哪里查 |
| --- | --- | --- |
| 想了解商品规格或使用规则 | 从商品页进入独立咨询会话，读取商品事实和对应资料 | 客服回答及来源 |
| 不记得订单号，或同类商品买过多次 | 我的订单筛选，或自然语言查询；多笔时明确选择 | 订单详情与候选卡 |
| 未发货，明确希望取消 | 查看确认卡后确认；放弃则不执行 | 持久动作结果、订单与退款记录 |
| 点确认后断网，不知道成功没有 | 刷新或返回客服页后只读核验 | 同一动作的最终决定 |
| 退款长时间没有明确结果 | 后台转人工，客服回复并重新核验原退款 | 订单、工单和新会话均可查 |
| 已签收，希望退回单件商品 | 提交原因，等待审核，按指引退回，客服确认收货 | 退货申请与最终退款进度 |
| 人工说处理好了，顾客仍有问题 | 在原工单补充消息，重新进入处理中 | 同一工单的持续对话 |
| 客服上传新资料时任务中断 | 系统恢复任务，失败后可人工重建 | 知识版本状态与活动版本 |

## 3. 四条重要业务链怎样实现

### 3.1 取消与退款：页面不知道结果，不等于后端没执行

例如顾客要取消已付款订单，Agent 先确定是哪一笔，再生成确认卡。确认卡绑定顾客、会话、订单版本和有效期。顾客确认后，后端重新核对这些条件，在同一事务中记录决定、取消订单、记录操作并创建退款与投递任务。

如果数据库已经提交，但返回页面的响应丢了，页面会查询原动作结果。它不会因为“没收到成功消息”就自动重新取消。后台退款也遵循相同思路：先查原退款编号，只有渠道明确没有受理或明确失败后进入新批次，才允许提交。

这条链主要体现的是副作用执行正确性。Redis Checkpoint 负责会话状态，MySQL 的动作、订单和退款账本才是判断业务是否发生的依据。

代码入口：[ActionDecisionService](../apps/serviceflow-server/src/main/java/com/serviceflow/service/ActionDecisionService.java)、[OrderConversation](../apps/serviceflow-server/src/main/java/com/serviceflow/agent/OrderConversation.java)、[系统架构](architecture/system-overview.md)。

### 3.2 已收货后退货：审核通过还不能直接退款

顾客从订单详情提交退货原因。后端检查本人归属、订单已签收且已付款、没有已有退款，并且只有一条商品明细、数量为 1。退款金额取原订单实付金额，前端不能自行提交退款金额。

客服审核时给出退回指引或拒绝原因。审核通过只说明允许退货。顾客按指引退回后，客服确认实物验收，后端才把“已收货、付款进入退款、唯一退款请求、后台任务”一起提交。重复点击收货返回原结果，不生成新退款。

每单目前只保留一张退货申请，已拒绝的申请不能再次申请。退回物流由顾客按指引办理，客服手工确认实际收货；尚未接快递下单、自动物流签收或部分退款。

代码入口：[ReturnService](../apps/serviceflow-server/src/main/java/com/serviceflow/service/ReturnService.java)、[顾客订单页](../apps/serviceflow-web/src/views/OrdersView.vue)、[退货管理页](../apps/serviceflow-web/src/views/ReturnsView.vue)。

### 3.3 人工工单：从一次回复变为能追踪的服务过程

顾客在“我的工单”打开问题，客服在运营中心接手。双方公开回复写入 `ticket_message`；内部处理备注留在内部字段，不进入顾客详情。

工单状态通常是 `OPEN → ASSIGNED → RESOLVED → CLOSED`。客服标记解决后，顾客补充问题会把它恢复为 `ASSIGNED`；顾客确认解决后才进入 `CLOSED`。关闭后不再允许追加回复。

每条回复由浏览器生成稳定 UUID。服务端锁定工单后校验 UUID、角色和内容；响应不明时再次提交同一条消息，只返回已保存的结果。这样，网络重试不会把一句回复写成两条，旧请求也不能用同一 UUID 改写内容。

工单列表和消息历史各显示最近 200 条。退款转人工的原工单也可以直接进入这套对话，不需要顾客再描述一次订单和背景。

代码入口：[TicketServiceImpl](../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/TicketServiceImpl.java)、[TicketDetailView](../apps/serviceflow-web/src/views/TicketDetailView.vue)、[V14 迁移](../apps/serviceflow-server/src/main/resources/db/migration/V14__ticket_conversation.sql)。

### 3.4 知识更新：旧任务晚完成，不能把资料改回旧版

同一文档上传新版本时，后端先锁定文档行再分配版本号。每次上传都有独立文件路径，避免两个同名文件互相覆盖。数据库事务回滚时清理本次新文件，不动原资料。

消费者领取任务后有三分钟租约，解析后与每个分块前续期。后台每 30 秒扫描超时任务。自动恢复最多三次；人工重建可另起一次尝试链。已发布但一直未领取的通知会重新投递，连续五次发布失败则转为 FAILED，供人工重建。

每次真正重试创建新版本编号，并引用原始文件。这样，即使旧工作线程后来恢复，它的向量写入也只会落到旧版本范围。激活前再次检查状态和租约，且只允许版本号向前推进。新资料没有完整入库之前，旧活动版本继续提供检索。

这解决了已覆盖的中断和并发问题，但 MySQL、文件和 Milvus 不是一个跨存储事务。历史失败版本及向量仍保留用于追溯。本次没有新增收费 Embedding 或真实 Milvus 写入故障实验；验证使用真实数据库状态以及受控检索接口。

代码入口：[KnowledgeServiceImpl](../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/KnowledgeServiceImpl.java)、[知识时序说明](architecture/system-overview.md#知识入库时序)、[V15 迁移](../apps/serviceflow-server/src/main/resources/db/migration/V15__knowledge_recovery.sql)。

## 4. Agent 负责什么，后端负责什么

模型负责理解开放的自然语言、生成有限种类的订单查询计划、选择与问题相关的商品证据。后端负责身份、参数、候选归属、金额、状态和执行权限，最终答案中的订单事实来自实际查询。

本次给明确订单号和限定的当前订单追问增加直接查询路径。例如已经选定订单后问“退款进度”，没有必要再请求一次意图分类和一次订单规划。只有完整匹配的表达进入此路径，且仍通过本人订单查询。投诉、取消和混合请求继续走原来的判定流程。

完整 LangGraph 工作流集成测试覆盖四类明确查询，并验证模型接口零调用；外部客户提供该订单号仍被拒绝。这证明这些确定查询能省去模型调用，不是对任意自然语言理解能力或 Cloud 实际时延的测量。

聊天执行前通过 SSE 发送处理进度，避免页面只有空白等待。指标 `serviceflow.chat.first_token_server` 记录服务端开始处理到第一段非空正文产生的时间，包含此前的业务与模型等待，不包含缓存重放，也不是浏览器端收到第一字的时间。

独立 AI 审计默认保存意图、来源、结果、耗时等元数据，不额外复制问题与答案正文。历史审计正文默认也不经该接口展示。原顾客聊天记录及历史数据仍保留；服务端可通过 `SERVICEFLOW_AUDIT_RECORD_CONTENT=true` 显式启用正文审计，Compose 使用时需要将该变量传入服务容器。

## 7. 怎样讲清这个项目的价值

可以从一个具体问题开始演示：“用户确认取消后断网了，而退款渠道又没有及时返回，系统如何避免让顾客重复退款、又让客服接得住？”然后展示持久动作结果、同编号退款核验、原工单跨会话查询以及最终关闭。

这里能用代码和测试说明的能力是：把模型理解连接到真实业务状态，明确谁授权了什么，在网络不可靠、请求重复、进程重启时继续取得可信结果。自然语言能力仍受模型和资料影响，公开商品资料与合成订单也不代表真实生产流量；这些边界应与已经验证的后端正确性一起如实说明。
