# ServiceFlow 项目评估与求职优化路线

评估日期：2026-10-23。代码基线：`f9a2666a`。目标：求职/作品集，展示完整业务与工程能力。

## 2026-10-25 当前求职方向与能力状态

ServiceFlow用于展示有状态业务Agent的工程实现：请求与会话重放、证据范围、客户确认、参数授权、事务副作用和未知结果核验。当前代码与取舍以[技术报告](technical-report.md)、[架构时序](architecture/system-overview.md)及[简历代码证据](portfolio/resume-project.md)为准；不以扩SKU、商城页面、中间件或用例数作为下一步目标。

**下文保留2026-10-23原评估及当时建议，仅用于回溯，不再作为当前待办或当前能力清单。**

---

结论：ServiceFlow 已具备有实质内容的工程骨架，但可复现的业务场景、运行数据和质量证据仍偏演示化。当前最值得投入的是扩大有来源的业务语料、建立独立评测、做完整售后闭环，而不是继续增加中间件或模型数量。

本文区分三类证据：本次直接读取的代码与数据、本次执行的离线检查、仓库历史报告。没有启动业务数据库、运行付费云评测或重新训练模型；数据库中的实际存量与线上运行状态不在本次结论范围内。

## 1. 当前项目处于什么阶段

| 维度 | 当前判断 | 依据与求职含义 |
| --- | --- | --- |
| 工程实现 | 有实质内容的个人工程项目 | 订单条件更新、事务幂等、Outbox、权限校验、SSE、知识活动版本均有代码 |
| 产品完成度 | 可演示原型，闭环尚浅 | 取消后退款停在处理中；人工工单以管理员状态流转为主 |
| 业务数据 | 有真实公开事实，但覆盖很窄 | 可复现商品基线只有 3 款，业务知识只有 4 份短文，订单都是种子夹具 |
| AI 效果证据 | 已有基线，但端到端指标偏乐观 | 用例重复、文件名级检索指标、关键词判分、缺少真正多轮执行 |
| 训练实验 | 有价值的独立 Grader 实验 | 来源隔离、双种子、验证集选模、失败案例披露；不是完整客服模型 |
| 当前可复现性 | 应优先修整 | 单元检查通过，但格式门禁失败，训练大文件在当前检出目录缺失 |

实际后端是一个分层单体应用，外围使用 Redis、RabbitMQ、MySQL 和 Milvus。没有必要为了简历把它描述成微服务，也没有现成证据要求拆服务。

### 已经值得保留的设计

- 商品结构化事实和文档证据分离，避免让说明书替代数据库价格和规格。
- 订单取消由后端权限、二次确认、事务、唯一幂等键和版本条件更新控制。
- 知识文档新版本完整入库后切换活动版本，上传事务同时写 Outbox。
- Grader 输出限制到合法候选 ID；失败时显式表达证据不足或降级。
- 已有模型协议测试、架构测试、集成测试源代码、可观测性和历史故障记录。

证据入口：[订单服务](../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/OrderServiceImpl.java)、[确认操作](../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/ChatActionServiceImpl.java)、[知识服务](../apps/serviceflow-server/src/main/java/com/serviceflow/service/impl/KnowledgeServiceImpl.java)、[RAG](../apps/serviceflow-server/src/main/java/com/serviceflow/rag/MilvusRagService.java)。

## 2. “数据不够真实”的具体含义

### 2.1 可复现业务基线

| 数据 | 当前仓库可证实的内容 | 缺口 |
| --- | --- | --- |
| 商品 | V2 将原有商品替换为 Pura 80、Pro、Ultra，共 3 个 SKU | 同品牌同系列、同类别，难以验证别名、跨代型号和多规格歧义 |
| 商品来源 | 规格内保存官网 URL、核验日期、价格快照说明 | 导入 API 尚没有规范的来源版本/批次追踪；日期字段不等于持续更新机制 |
| 知识 | 3 份商品使用说明 + 1 份保修政策 | 缺长文、表格、版本差异、真实条件冲突、操作排障步骤 |
| 用户/订单 | 1 个种子客户，V1 两单 + V5 十九单，即 21 单 | 所有种子订单属于同一客户，初始以 PROCESSING/SHIPPED 和已支付状态为主 |
| 工单 | 用户投诉或确认转人工后创建 | 缺客户继续追问、客服逐条回复、处理时间线和客户确认入口 |
| 真实访问 | 仓库未提供可据以证明的持续真实用户样本 | 不能把本地回归或生成样例描述为商业流量 |

本次按 UTF-8 解码后统计，4 份知识文件分别为 562、648、605、669 个字符，总计 **2,484 个字符**，含标题、来源 URL 等元数据；这是文件字符数，不是 token 数或净正文汉字数。

[DocumentConsumer](../apps/serviceflow-server/src/main/java/com/serviceflow/infrastructure/messaging/DocumentConsumer.java) 当前采用 2,000 字符窗口。若只上传这 4 份文件，每份约形成一个块；商品检索又按 productId 过滤，某个型号通常只有一块候选。由此推断：当前样本无法充分检验 Dense/BM25/RRF/Rerank 组合在大量干扰材料中的增益。实际 Milvus 可能有额外上传文件，本次没有查询其存量。

### 2.2 不应混为一谈的三种“真实”

1. **事实真实**：规格、手册、政策有可追溯来源。项目已有基础。
2. **表达真实**：用户会说简称、错字、半句话、连续改口，且不会总给出精确型号。项目证据不足。
3. **过程真实**：订单状态变化、重复回调、失败恢复、客服回复和客户反馈形成可追踪过程。项目只实现部分环节。

求职项目可以使用合成订单；关键是明确标注 synthetic，并让约束、状态变化和失败行为可信。获取真实个人订单不是必要前提。

## 3. 当前评测为什么会显得“容易”

### 3.1 本次对 200 条评测集的统计

| 组 | 记录数 | 不同问题文本数 |
| --- | ---: | ---: |
| product-doc | 50 | 12 |
| policy | 50 | 50 |
| detail | 20 | 3 |
| compare | 20 | 3 |
| order | 20 | 20 |
| support | 20 | 13 |
| edge | 20 | 11 |
| 总计 | 200 | 112 |

按“问题 + 身份 + 页面上下文”计算，有 **124 个不同输入组合**。重复问题可能用于覆盖不同身份，不应一概删除，但不能把 200 条记录当作 200 种独立需求。当前没有 expectedIntent=CHAT 的用例；90 条检查商品 ID、130 条检查引用，而报告部分准确率以全部 200 条为分母，未要求该项的样本会自动通过。

数据源：[serviceflow-eval-200.json](../quality/evaluation/datasets/serviceflow-eval-200.json)。

### 3.2 判分与测试路径的局限

- `run-evaluation.ps1` 每条新建会话，仅发送一次问题；没有预置历史和多轮步骤，不能证明“刚才那个订单”等上下文能力。
- 取消订单用例只请求聊天接口，没有继续调用确认接口并校验数据库最终状态；成功弹出 action_required 不等于取消业务完整通过。
- `requiredFacts` 实际按“任意一个短语出现”通过，不是所有必需事实满足；否定语义也没有被判别。
- `forbiddenClaims` 只检查指定短语未出现。模型即使编造其他内容也可能通过，不能称为完整事实幻觉率。
- 公开结果只保留前 240 字回答摘要。线上第一次评分使用完整 tokenText，但离线标签修订依赖摘要，无法完整复核长回答。
- `audit-evaluation-report.ps1` 的 Recall/MRR/nDCG 根据最终引用文件名计算，既不是召回阶段 chunk 排名，也不是重排阶段独立评价。
- 所谓“没有登录时上传知识”的部分 edge 用例主体实际为 CUSTOMER；它测试的是非管理员回答边界，不等于未认证 HTTP 上传被拦截。
- 当前 Playwright 三条用例使用 `page.route/fulfill` 模拟商品、登录、聊天接口。它们是有用的前端流程测试，但不能替代浏览器穿过真实后端和数据库的验收。

证据：[在线执行器](../scripts/evaluation/run-evaluation.ps1)、[离线审计器](../scripts/evaluation/audit-evaluation-report.ps1)、[浏览器测试](../apps/serviceflow-web/e2e/visitor-product-flow.spec.ts)。

### 3.3 对历史结果应怎样表述

可以说：“在固定的 200 条回归记录上，一次云端运行原始规则通过率为 83.5%；更正部分冲突标签后离线审计为 98.5%，保留两版结果。”

不宜据此说：“真实客服正确率 98.5%、全系统幻觉率 0%、大规模检索 Recall@5 达 97.69%。”

Demo 压测与云端 AI 延迟需要分别报告：历史 Demo SSE P95 为 30 ms，历史云评测端到端 P95 为 17,689 ms。前者没有云模型链路，不能用于推导后者的用户体验或吞吐能力。虚拟线程开/关历史对照也没有证明显著性能优势。

## 4. 业务与实现中最值得补齐的部分

| 优先级 | 发现 | 改进方向 | 验收证据 |
| --- | --- | --- | --- |
| P0 | 评测口径和文档偏离当前状态 | 建立一份当前能力/限制清单；区分历史实验、当前代码、当前可运行产物 | README、演示脚本、简历描述使用同一组限定准确的指标 |
| P0 | V5 迁移中重置已有订单状态、退款状态并删除 order_operation | 将未来演示夹具与正式 schema 迁移分离；为已发布迁移制定兼容方案，不能直接改历史 checksum | 新演示库可初始化；已有库升级不重置业务记录 |
| P1 | 退款仅被设为 PROCESSING | 实现一个明确标注 sandbox 的退款任务/回调闭环 | 成功、失败、重复回调、状态冲突均可演示；重复事件不重复改变资金状态 |
| P1 | 工单只有简单状态推进 | 客户工单详情、客服回复、消息时间线、客户补充与确认解决 | 客户可看到客服处理结果；两个身份的真实端到端用例通过 |
| P1 | 无商品别名表，识别依赖正则和字符串 | 先处理高确定性订单号/SKU，再规范化别名；歧义时澄清 | 用简称、错字、跨代同名、无 pageContext 等独立题验证 |
| P1 | 商品分支未把 docs.sufficient 显式传入最终生成 | 保留可回答的数据库事实，同时传递证据是否充分和缺失范围 | 部分证据可回答已知部分，但不得补齐未支持能力；Grader 故障用例覆盖到最终回答 |
| P1 | 政策回答直接拼接证据正文 | 增加“适用条件—可执行下一步—证据位置”的回答格式；缺关键信息时澄清 | 用户询问具体情形时得到针对性答案，而不只是整份政策 |
| P1 | 消费者崩溃后 PROCESSING 缺恢复路径 | 增加有边界的过期任务识别/人工恢复；避免把仍在处理的任务错误接管 | 在 markProcessing 后终止进程，再启动，版本能够完成或进入可重试失败状态 |
| P1 | 同文档并发上传用 MAX(version)+1，保存路径相同 | 原子分配版本号，文件使用独立临时/唯一路径，再完成元数据登记 | 并发上传不会覆盖或删除另一请求已保存文件 |
| P2 | 产品管理只做 upsert，缺导入来源与差异记录 | 添加小型来源清单、批次 ID、校验报告、变更预览 | 能回答某个价格/规格来自哪里、何时更新、发生何种变化 |
| P2 | 审计缺检索阶段与完整复现上下文 | 在本地评测模式记录候选 ID、版本、排序、输入上下文、各阶段耗时 | 单个失败用例能定位到路由、召回、重排、Grader 或生成 |

## 5. 数据建设方案

### 5.1 先把一个垂直场景做好

建议继续做“中文 3C 商品售前与售后客服”，先保留华为作为主要来源，扩展多个型号和少数相关品类。另设一个有明确规则的模拟商店：厂家保修政策与商店退换货规则必须区分，不能把厂家资料当作商店履约承诺。

第一轮建议目标属于工作量预算，不是行业标准或性能保证：

| 层次 | 第一轮目标 | 构建要求 |
| --- | --- | --- |
| 商品事实 | 20–30 个可核验 SKU，覆盖多个系列及规格 | 统一规格单位、型号/地区/版本、来源 URL、获取日期、价格类型；别名单独维护 |
| 业务知识 | 80–150 份有内容差异的 FAQ、手册章节或政策材料 | 包含长文和条件限定；不靠同一短文改写扩数量；保存章/节/页位置 |
| 业务夹具 | 5–10 个合成客户，30–50 个独立场景 | 未支付、已支付、已发货、取消、退款成功/失败、物流异常、越权与重复事件 |
| 规模数据 | 有需要时生成 1,000 条订单用于分页和筛选 | 与业务场景集分开；只有查询退化或压测需求出现时才扩到更大规模 |
| 人类提问 | 邀请 5–10 人各进行若干自由咨询，形成首批 50–100 个会话 | 告知用途，保留原始用语；不能称为真实商业订单或真实付费用户流量 |
| 独立评测 | 200–300 个去重单轮问题 + 30–50 个多轮场景 | 测试在优化前冻结；按来源、商品家族、问题模板分组，留出未见组合 |

已有训练报告记载的 84 个官网页面可以作为来源选题线索，但当前检出中缺其快照。应重新核对来源与版本，不把含模拟发布通道、注入文本或训练目标的 Grader 夹具直接导入业务知识库。

### 5.2 查证过的外部来源与用途

以下入口于 2026-10-23 查证。这里只研究适配性，没有下载全集、申请数据或联系提供者。

| 来源 | 适合本项目的用途 | 限制与优先级 |
| --- | --- | --- |

| [JDDC 2.1 官方项目](https://github.com/hrlinlp/jddc2.1) | 中文电商多轮表达、指代、查询改写、摘要与客服场景 | 领域最匹配；官方页面要求填写申请表并用机构邮箱申请。不能假设立即可下载，申请等待不应阻塞项目主线 |
| [MobileCS / SereTOD 官方项目](https://github.com/SereTOD/SereTOD2022) | 真实中文客服的省略、纠错、上下文与槽位表达 | 10 万真实对话、其中 1 万标注；领域为运营商客服。官方规则有数据使用协议和审批，不能直接把业务标签映射成手机售后事实 |
| [Bitext 客服数据卡](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset) | 构建意图分类的语言变体和错误拼写开发集 | 26,872 对，27 种意图，英语混合合成数据，数据卡标注 CDLA-Sharing-1.0。适合作辅助；不能称真实客服日志，也不能直接使用其回复作为商店政策 |
| [Amazon Reviews 2023 官方入口](https://amazon-reviews-2023.github.io/) | 商品目录检索、缺失元数据处理、评论中问题表达的独立实验 | 有商品元数据与评论；英语和历史快照为主，不能提供当前中文商店价格或订单状态。本轮优先级较低 |

采用外部对话时，先区分“保留原始语料的语言测试”和“替换成项目实体后重建的场景”。改写后的样本应明确标注 derived/synthetic，不能继续冒充原始真实对话。外部客服回答中的承诺和价格不得进入项目事实表。

### 5.3 最小数据管道

流程：来源登记 → 原文快照/许可记录 → 事实提取 → 人工或明确标注身份的复核 → 格式校验与去重 → 差异预览 → 调用现有导入/上传接口 → 记录导入版本。

最少元数据：source_id、source_url、source_revision、fetched_at、applicable_models、region、software_version、effective_time、synthetic、review_status、import_batch_id。按适用性使用字段，不需要为了整齐让所有来源强行填满。

业务事实、知识正文、对话样本、评测答案分别管理。价格由事实表维护；订单由业务服务维护；检索证据不能授权修改订单。

## 6. 评测应怎样升级

1. **保留旧基线。** 原始 200 条和原始报告不覆盖；另建版本化开发集和保留测试集，标注重复题的意图。
2. **执行真正的场景。** 支持 setup、同会话多个 turn、确认动作和最终断言；越权测试直接请求受保护 API。将成功、拒绝、异常、取消确认分别统计。
3. **把指标分层。** 路由用 Macro-F1 和混淆矩阵；实体用精确匹配/歧义澄清率；召回和重排用各自 chunk 级标签；生成用正确性、完整性、证据支持；业务操作看最终数据库事实。
4. **修正分母。** 只在有商品标注的样本上计算商品识别；只在可答/应拒答对应切片上计算相关指标。报告分子/分母，不把不适用项算成功。
5. **加入有区分度的反例。** 同名不同规格、型号相邻、版本过期、否定答案、条件不满足、只支持两问中的一问、跨客户订单、重复确认、用户改口、CHAT 和超出服务范围。
6. **先改观测，再改算法。** 本地保存完整脱敏回答与检索轨迹，记录 Git、数据/知识版本、Prompt、各阶段模型、耗时、输入输出 token；公开只发布经过复核的派生报告。
7. **用最小对照证明组件价值。** 固定知识与保留题，对比 BM25、Dense、Hybrid；再比较 Hybrid 与加 Rerank 的差异，最后比较 Grader 的错误接受/错误拒绝与成本。引用同一份缓存候选时说明评测层级。
8. **人工校准。** 首批至少逐条复核 100 条，并重点复核系统间分歧；自动裁判只能辅助，不能以同一模型的自评替代独立判断。

可预登记的第一轮工程目标：30 个关键场景全部满足业务最终态；跨客户越权和重复副作用为 0；所有公开事实都有来源；模型分项效果较基线改善且公开退步样例。自然语言正确率、延迟和成本目标应先用新基线测量后确定，不承诺未经验证的 99%。

## 7. 已有 SFT 应如何利用

现有 [Grader 实验报告](../training/reports/grader-specialist-exp-01-results.md) 是项目的亮点之一：按来源分组，600/120/180 划分，双种子训练，验证集选择 epoch，保留模型失败和测试边界。

但它也明确披露 AI 编写/审核、无独立人工复核、跨集合模板结构共享。历史报告中主种子新测试为 180/180，而旧压力 Grader 为 40/60，范围干扰仅 1/10；这说明当前最需要的是更真实的适用范围难例和实际检索候选，不是继续把同一种模板生成到几万条。

下一步顺序：

- 整理可合法公开的小型数据卡、派生统计、复现步骤和模型取得方式，使别人能理解与复核实验。
- 从扩充后的 RAG 检索中抽取真实候选构建 Grader 评测，补人工审查，允许多个等价支持集合。
- 保持冻结测试不参与训练和调参；修复已知模板捷径并用新来源/新表达留出集复测。
- 只为 `evaluateEvidence` 接入专用 Grader，保持 Chat、Intent、Rewrite 的模型边界。当前 CloudAiGateway 共用一个 StreamingChatModel，直接更改全局 OPENAI_MODEL 会影响多项任务。
- 先做离线或影子对照，比较错误接受、错误拒绝、端到端耗时与实际算力成本，再决定是否成为默认链路。

本次 `python -B training/cli.py status` 显示 model、adapter、checkpoint、dataset 四个路径均不存在。此结论只针对当前检出，不判断其他机器上是否仍保存产物；历史报告不是本次重新运行的模型实测。

## 8. 建议的实施顺序与工作量

按单人约 4–6 周有效开发时间估算；官方数据申请不纳入关键路径。以下是规划，不是已完成项。

| 阶段 | 预计投入 | 具体交付 | 完成标准 |
| --- | --- | --- | --- |
| A：可信基线 | 1–2 天 | 当前能力清单；文档口径修正；格式/EOL 门禁修复；数据统计报告 | 明确哪些指标可复现，标准本地检查通过或有明确环境限制 |
| B：数据与评测 | 4–6 天 | 20–30 SKU、80–150 份材料、场景夹具、多轮执行器、冻结测试集 | 来源可追溯、按组隔离；初始失败分布可定位 |
| C：一条售后闭环 | 5–7 天 | 客户订单入口、取消确认、sandbox 退款回调、客户工单详情/回复/结果 | 客户→系统→客服→客户完整演示，重复请求与越权不改变错误对象 |
| D：AI 效果改进 | 4–6 天 | 别名解析、部分证据处理、针对性政策回答、检索对照、Grader 实际候选评测 | 分项效果、失败案例、延迟/成本均有可复核报告 |
| E：交付与展示 | 2–3 天 | 无 API mock 的关键 E2E、知识入库故障演练、受控小并发、演示视频/README | 新环境能运行公开基线，5–8 分钟演示能展示业务与异常路径 |

只有两周时，优先完成 A、B 的最小版本，以及 C 中“取消→退款回调→客户结果”的一条完整路径；暂缓新模型训练、多品类大规模扩展和复杂运营报表。

建议第一批小任务：

1. 统一当前说明和格式门禁，给历史评测补清楚口径。
2. 为数据集增加重复输入、CHAT 缺失、分项分母统计；建立新版本多轮用例。
3. 把样例数据初始化与未来结构迁移分开，保留历史迁移兼容性。
4. 新增来源登记及别名数据，从 3 款扩到 20 款。
5. 对“确认取消、退款回调、重复回调、另一客户访问”做一条真正穿透后端的自动化场景。

## 9. 本阶段不建议投入的方向

- 拆微服务、增加 Kubernetes、再换消息队列：没有解决当前最明显的数据和闭环缺口。
- 加多 Agent、GraphRAG、NL2SQL：尚未证明当前检索链路在有难度的语料上的效果，也没有对应的复杂业务需求。
- 直接再生成几万条 SFT：模板偏差和真实检索分布问题会被放大。
- 为“看起来企业级”堆全电商：客服项目可以接订单沙箱，不必再实现完整商城、营销、支付平台。
- 先换掉所有既有基础设施：已有 Redis、RabbitMQ、Milvus 各有明确路径；优先用故障演练和对照说明它们的价值。
